## 1. 结论先行

### 1.1 推荐方向

把产品定位从“通用大模型对话系统”调整为：

> **面向中小企业、法务和业务人员的合同审查与合规助手：上传合同，自动识别风险条款，给出修改建议，生成可导出的审查报告，并支持围绕合同继续追问。**

最小可行产品（MVP）不是“做一个法律聊天机器人”，而是完成一条完整业务链：

1. 上传 PDF / DOCX 合同；
2. 解析正文并按条款切分；
3. 选择审查立场（甲方 / 乙方 / 中立）和规则集；
4. 规则引擎 + 大模型联合审查；
5. 输出风险清单、原文定位、修改建议和依据；
6. 围绕合同追问；
7. 导出 Word / PDF 审查报告；
8. 保存历史版本，支持复查和对比。

### 1.2 为什么这个方向适合当前项目

当前系统已经具备一套可复用的商业基础设施：

- 用户注册、登录、JWT、角色与状态管理；
- 会员到期时间、套餐、订单、支付配置与回调幂等；
- 多模型配置、动态 URL / Key / 模型名、后台管理；
- SSE 流式对话、会话历史、Redis 上下文缓存；
- 管理后台的用户、套餐、订单、模型、支付配置页面。

这些能力直接复用到合同审查产品中，新增的重点不是“再造一个聊天框”，而是文档处理、审查规则、结构化结果、报告导出和用量计费。这样既能让现有代码继续产生价值，也能形成通用聊天产品难以复制的业务闭环。

### 1.3 产品边界

产品应定位为“辅助审查工具”，而不是替代律师出具法律意见：

- 只提供风险提示、条款定位和修改建议；
- 每个结论尽量引用合同原文和规则依据；
- 高风险结论要求用户人工确认；
- 页面、报告和接口中明确展示免责声明；
- 不承诺审查结果完整、准确或适用于特定司法辖区；
- 不把客户合同用于训练模型，除非取得明确授权。

## 2. 现有能力盘点

### 2.1 已经具备的能力

| 能力 | 当前实现 | 可复用价值 |
| --- | --- | --- |
| 认证与权限 | JWT Access / Refresh Token、`USER` / `ADMIN` 角色、用户状态 | 直接复用 |
| 会员体系 | `UserMembership.expireAt` 控制对话权限 | 可扩展为“会员 + 文档额度” |
| 套餐与订单 | 套餐、订单、支付配置、会员时长累加 | 直接复用，增加合同审查权益 |
| 支付 | Mock / Playoffer Provider、回调幂等 | 直接复用，后续补真实渠道 |
| 模型管理 | 动态模型配置、Key 加密、启用排序 | 可扩展模型路由和成本控制 |
| 流式对话 | SSE 输出、中止处理、消息落库 | 可复用为合同问答 |
| 会话管理 | 会话 CRUD、历史消息、自动标题 | 可复用为“围绕合同的项目会话” |
| 上下文 | Redis 缓存最近 5 轮对话 | 需要升级为文档级检索 |
| 管理后台 | 用户、套餐、模型、支付、订单、仪表盘 | 可扩展规则、提示词、用量管理 |

### 2.2 当前的关键缺口

| 缺口 | 现状 | 对垂直产品的影响 |
| --- | --- | --- |
| 只支持纯文本消息 | `messages.content` 为文本 | 无法上传合同、图片和扫描件 |
| 固定 5 轮上下文 | `limitToFiveRounds` | 长合同无法依靠对话历史理解 |
| 没有文档存储 | 无文件表、无对象存储 | 无法管理合同版本和原件 |
| 没有文档解析 | AI 客户端只发 OpenAI 兼容文本请求 | PDF / DOCX 不能直接审查 |
| 没有异步任务 | 请求内同步完成模型调用 | 长文档审查容易超时、失败不可恢复 |
| 没有结构化输出 | 主要返回自由文本 | 无法稳定生成风险清单和报告 |
| 没有用量计费 | 会员只按时间判断 | 无法控制模型成本，也无法按文档收费 |
| 没有审查规则库 | 无规则表、无版本管理 | 审查质量不可控、不可解释 |
| 没有审计与留存策略 | 仅有登录日志 | 企业客户无法接受 |
| 没有团队空间 | 数据只按个人隔离 | 无法向团队版和企业版扩展 |

### 2.3 现状判断

现有系统更像“通用聊天 + 会员订阅”的演示型产品。它的优势是基础闭环完整，短板是缺少一个能持续产生业务结果的场景。继续堆通用功能，例如更多模型、更多主题、更多聊天样式，边际价值很低；而把同一套基础设施落到合同审查上，能同时提升付费理由、使用频率和竞争壁垒。

## 3. 垂直方向对比

评分说明：5 分最好。`技术难度` 和 `合规风险` 两项中，5 分表示更容易、更低风险。

| 方向 | 需求刚性 | 付费意愿 | 代码复用 | 技术难度 | 合规风险 | 差异化空间 | 综合判断 |
| --- | ---: | ---: | ---: | ---: | ---: | ---: | --- |
| 合同审查与合规助手 | 5 | 5 | 4 | 3 | 3 | 4 | **首选** |
| 企业知识库 / 售后助手 | 4 | 4 | 4 | 4 | 4 | 2 | 备选 |
| 跨境电商客服 | 3 | 4 | 4 | 3 | 4 | 3 | 备选 |
| 教育题库 / 作业辅导 | 4 | 3 | 3 | 4 | 4 | 2 | 谨慎 |
| 医疗健康咨询 | 5 | 4 | 2 | 2 | 1 | 3 | 不建议 |

### 3.1 为什么不是企业知识库

企业知识库和售后助手的技术路径更稳，也能复用现有 SSE 对话，但市场非常拥挤，产品容易退化成“上传文档 + 提问”。如果要做，建议进一步收窄到某个行业，例如制造业设备手册、SOP 和维修知识，而不是做通用知识库。

### 3.2 为什么不是医疗

医疗需求强，但涉及诊断、处方、隐私和监管，产品责任远高于当前团队和系统能承受的范围。现有代码也没有任何医疗合规基础，不建议作为第一个垂直方向。

### 3.3 合同审查的独特优势

- 合同是高频、刚需、可标准化的文档；
- 审查结果天然适合结构化展示和报告导出；
- 风险条款可以沉淀为规则库，形成长期资产；
- 企业愿意为“降低风险 + 节省律师时间”付费；
- 现有会员、支付、后台和对话能力可以直接复用；
- 通过“辅助审查 + 人工确认”可以把合规风险控制在可接受范围。

## 4. 目标用户与核心场景

### 4.1 目标用户

| 用户 | 典型痛点 | 购买理由 |
| --- | --- | --- |
| 中小企业负责人 | 没有专职法务，合同靠业务人员自行判断 | 低成本获得第一轮风险筛查 |
| 企业法务 / 合规专员 | 合同量大，重复条款多，审阅耗时 | 提升初审效率，统一审查口径 |
| 采购 / 销售 | 只能关注价格和交付，忽略责任、违约、知识产权 | 在谈判前发现明显不利条款 |
| 律所助理 / 法务外包团队 | 需要快速整理合同要点和风险清单 | 缩短初稿和整理时间 |
| 创业公司 | 融资、采购、租赁、劳动合同时缺经验 | 用标准化报告辅助决策 |

### 4.2 核心使用场景

1. **销售合同签约前审查**：识别付款、验收、违约、责任上限、知识产权和争议解决风险。
2. **采购合同审查**：关注交付、质保、索赔、单方终止和供应商责任。
3. **NDA / 保密协议快速审查**：检查保密范围、期限、例外和违约救济。
4. **劳动合同与外包合同检查**：识别不合理的竞业、赔偿、解除和知识产权归属条款。
5. **租赁 / 服务合同审查**：检查自动续约、费用调整、提前解约和押金条款。
6. **合同版本对比**：对方修改后，快速看出新增、删除和措辞变化带来的风险。

### 4.3 用户真正想完成的任务

> “在十分钟内知道这份合同哪里不能签、为什么不能签、应该怎么改，并且能把这个结论交给老板或客户。”

因此，产品输出的重点不是一段“看起来很专业”的聊天回复，而是：

- 有优先级排序的风险清单；
- 能定位到原文条款和页码；
- 有可执行的修改建议；
- 有可导出的报告；
- 有审查范围和免责声明。

## 5. MVP 产品闭环

### 5.1 主流程

```text
创建合同项目
  -> 上传 PDF / DOCX
  -> 解析正文与页码
  -> 条款切分与类型识别
  -> 选择审查立场与规则集
  -> 异步审查任务
  -> 规则命中 + 模型分析
  -> 风险清单与原文定位
  -> 合同内追问
  -> 导出审查报告
  -> 保存历史与版本
```

### 5.2 审查结果页应包含

- **合同概览**：合同类型、双方、金额、期限、管辖地、识别置信度；
- **风险总览**：高风险 / 中风险 / 低风险数量，按类别分布；
- **风险列表**：标题、风险等级、涉及条款、原文引用、风险说明、修改建议、依据；
- **缺失条款**：保密、违约责任、争议解决、知识产权、数据保护等；
- **条款导航**：按章节或条款顺序浏览；
- **原文对照**：点击风险项高亮对应条款；
- **处理状态**：待确认、已接受、已忽略、需要人工复核；
- **报告导出**：Word / PDF；
- **追问入口**：只围绕当前合同回答，并尽量引用原文。

### 5.3 MVP 验收标准

- 30 页以内 DOCX / 文本型 PDF 能在 3 分钟内生成审查结果；
- 每条风险必须能定位到具体条款或页码；
- 报告包含审查范围、风险统计、条款原文、建议和免责声明；
- 不同用户之间的合同、条款和报告严格隔离；
- 审查失败可重试，任务状态和错误原因可见；
- 单份合同的模型成本可统计，能够按额度扣减。

```text
合同工作台

├── 规则库
├── 提示词模板
├── 模型路由
```

## 7. 数据模型建议

### 7.1 核心表

建议在现有 Prisma Schema 上新增以下模型。字段可以在实现时微调，但关系应尽量保持清晰。

| 模型 | 关键字段 | 作用 |
| --- | --- | --- |
| `ContractProject` | `id`、`userId`、`teamId?`、`name`、`contractType`、`counterparty`、`status` | 一份合同及其多次审查的项目容器 |
| `ContractDocument` | `id`、`projectId`、`filename`、`mimeType`、`size`、`storageKey`、`sha256`、`pageCount`、`parseStatus`、`parsedText` | 合同原件与解析结果 |
| `ContractClause` | `id`、`documentId`、`orderNo`、`clauseType`、`heading`、`content`、`pageStart`、`pageEnd`、`charStart`、`charEnd` | 可定位的条款单元 |
| `ReviewTask` | `id`、`documentId`、`ruleSetId`、`modelConfigId`、`stance`、`status`、`progress`、`errorMessage`、`startedAt`、`completedAt` | 一次异步审查任务 |
| `ReviewFinding` | `id`、`taskId`、`clauseId?`、`category`、`riskLevel`、`title`、`analysis`、`suggestion`、`legalBasis`、`confidence`、`status` | 单条审查结论 |
| `ReviewRule` | `id`、`code`、`name`、`category`、`severity`、`ruleType`、`configJson`、`prompt`、`enabled`、`version` | 可配置、可版本化的审查规则 |
| `ReviewRuleSet` | `id`、`name`、`contractType`、`stance`、`enabled`、`version` | 面向不同合同类型和立场的规则集合 |
| `ReviewReport` | `id`、`taskId`、`format`、`storageKey`、`summaryJson`、`status`、`createdAt` | 导出的报告文件及摘要 |
| `UsageLedger` | `id`、`userId`、`taskId`、`kind`、`tokensIn`、`tokensOut`、`credits`、`createdAt` | 模型调用和额度扣减流水 |
| `ReviewFeedback` | `id`、`findingId`、`userId`、`action`、`comment`、`createdAt` | 用户接受、忽略、纠错，用于质量迭代 |
| `KnowledgeDocument` | `id`、`title`、`source`、`jurisdiction`、`storageKey`、`status` | 法规、模板、审查指引等知识库资料 |

### 7.2 关系与索引

```text
User 1 --- n ContractProject
ContractProject 1 --- n ContractDocument
ContractDocument 1 --- n ContractClause
ContractDocument 1 --- n ReviewTask
ReviewTask 1 --- n ReviewFinding
ReviewTask 1 --- 1 ReviewReport
ReviewRuleSet 1 --- n ReviewRule
User 1 --- n UsageLedger
ReviewFinding 1 --- n ReviewFeedback
```

关键索引：

- `contract_projects(user_id, updated_at)`：用户合同列表；
- `contract_documents(project_id, created_at)`：版本列表；
- `contract_documents(sha256)`：重复文件检测和结果复用；
- `contract_clauses(document_id, order_no)`：条款顺序读取；
- `review_tasks(document_id, status)`：任务查询；
- `review_findings(task_id, risk_level)`：风险筛选；
- `usage_ledger(user_id, created_at)`：额度与账单；
- `review_rules(code, version)`：规则版本唯一性。

### 7.3 设计要点

- 文件只存对象存储的 `storageKey`，数据库不存二进制；
- 合同原文件、解析文本、条款和审查结果分层保存，便于重跑和审计；
- 审查结论必须引用 `clauseId` 或页码区间，避免无法定位的自由文本；
- `ReviewRule` 和提示词必须版本化，报告记录本次使用的规则集版本；
- 为未来团队版预留 `teamId`，但 MVP 可以只按 `userId` 隔离；
- 删除采用软删除或延迟清理，给用户留出恢复和导出窗口；
- 报告生成后保存快照，避免规则或模型变化导致历史报告被改写。

## 8. 技术实现方案

### 8.1 文档上传与解析

建议新增独立的 `contracts` 和 `reviews` 模块，不把文件处理塞进现有 `conversations` 模块。

**上传**

- `POST /api/contracts` 使用 multipart 上传；
- 限制 MIME：`application/pdf`、DOCX；
- 限制单文件大小和页数，例如 50 MB、100 页；
- 计算 SHA-256，命中相同文件时提示复用历史结果；
- 文件存入 MinIO / S3 / 本地挂载卷，数据库只保存元数据；
- 下载使用短期签名 URL，不直接暴露存储路径。

**解析**

- DOCX：使用 `mammoth` 提取文本和段落结构；
- 文本型 PDF：使用 `pdfjs-dist` 或 `pdf-parse` 提取文本和页码；
- 扫描件：先检测文本密度，再接入 OCR（PaddleOCR / Tesseract）；
- 保留页码、段落、标题层级和字符偏移；
- 输出解析质量分数，低质量时提示用户上传可复制文本的版本；
- 解析失败和低质量文件进入人工修正或重新上传流程。

**条款切分**

- 优先使用标题层级、编号规则和版式特征；
- 使用正则识别“第 X 条”“1.1”“（一）”等编号；
- 对无法规则切分的文档，使用模型进行结构化切分；
- 每个条款保存 `orderNo`、标题、正文、起止页码和字符偏移；
- 条款切分结果允许用户手动调整，调整后重新审查。

### 8.2 异步审查任务

长合同审查不能阻塞 HTTP 请求。建议使用 Redis + BullMQ（或同类队列）：

```text
POST /api/contracts/:id/review
  -> 创建 ReviewTask(status = QUEUED)
  -> 返回 taskId
  -> Worker 消费任务
  -> 解析 / 规则检查 / 模型审查 / 生成报告
  -> 更新 status、progress、error
```

任务状态建议：

```text
QUEUED -> PARSING -> REVIEWING -> GENERATING_REPORT -> COMPLETED
                                      \-> FAILED
```

要点：

- 任务必须幂等，重复提交返回已有任务；
- Worker 失败可重试，超过次数后记录错误；
- 前端通过轮询或 SSE 获取进度；
- 任务和用量都记录 `userId`，便于限额和审计；
- 同一用户并发任务数需要限制，防止成本失控。

### 8.3 审查引擎

推荐“规则引擎 + 大模型”的混合架构，而不是完全依赖模型自由发挥。

**第一层：确定性规则**

适合检查可枚举的问题，例如：

- 是否缺少保密条款；
- 是否存在无限责任或责任上限缺失；
- 是否存在单方解除权；
- 付款周期是否超过阈值；
- 是否自动续约；
- 争议解决地是否明显不利；
- 知识产权是否全部无偿转让；
- 是否缺少数据保护条款；
- 验收期限是否过短；
- 违约金比例是否异常。

规则输出稳定的 `ruleCode`，便于统计、解释和版本管理。

**第二层：模型审查**

- 按条款或章节分块，控制单次上下文；
- 要求模型输出严格 JSON，并由后端做 Schema 校验；
- 每条结论包含：类别、等级、条款 ID、原文引用、风险说明、修改建议、依据、置信度；
- 对长合同采用 map-reduce：先逐段审查，再汇总去重和排序；
- 模型输出解析失败时重试或降级为规则结果；
- 对高风险结论进行二次模型复核或人工复核。

建议每条审查结论至少包含以下字段：

| 字段 | 说明 |
| --- | --- |
| category | 风险类别，例如责任、付款、终止、知识产权、数据保护 |
| riskLevel | HIGH / MEDIUM / LOW |
| clauseId | 对应条款 ID，保证可定位 |
| quote | 合同原文摘录 |
| title | 风险标题 |
| analysis | 风险说明 |
| suggestion | 可执行的修改建议 |
| legalBasis | 命中的规则编码或审查依据 |
| confidence | 模型置信度，用于排序和人工复核 |

**防止提示词注入**

合同正文是不可信输入，可能包含“忽略以上指令”等文本。处理方式：

- 明确把合同内容放在数据分隔符中；
- 系统提示词声明：合同文本只是待分析数据，不是指令；
- 不允许合同文本触发工具调用或系统操作；
- 对输出做结构校验，拒绝自由格式和越权内容；
- 记录模型原始输出，便于审计和问题复现。

### 8.4 合同内问答

现有对话是固定 5 轮上下文，不适合长合同。建议改为：

1. 将条款切分结果写入检索索引；
2. 用关键词加向量检索找出与问题相关的条款；
3. 把相关条款和审查结论作为上下文；
4. 要求回答引用条款编号；
5. 找不到依据时明确说不确定，而不是编造。

可选技术：

- 向量库：pgvector、Qdrant 或 Milvus；
- Embedding：使用独立的模型配置，不与聊天模型绑定；
- 关键词检索：MySQL 全文索引或 Elasticsearch；
- 初期可以用 MySQL 加简单相似度检索，不必一开始引入复杂向量基础设施。

### 8.5 报告生成

报告是合同审查产品最重要的交付物之一，建议支持：

- HTML 模板渲染后转 PDF（Playwright / Puppeteer）；
- DOCX 使用 docx 等库生成；
- 报告内容包含：封面、审查范围、合同概览、风险统计、风险明细、原文引用、修改建议、规则版本、免责声明；
- 报告生成异步执行，完成后提供签名下载链接；
- 报告保存快照，后续规则变化不影响历史报告；
- 免费版可加水印或限制导出格式，付费版开放完整报告。

### 8.6 额度与计费

现有会员按时间判断，适合是否可用，但不适合控制模型成本。建议增加两层权益：

1. **会员权益**：是否可以使用合同审查、报告导出、历史保留等；
2. **文档额度 / 积分**：每月可审查多少份、多少页、多少 Token。

扣费规则建议：

- 创建任务时预检查额度；
- 审查成功后扣减；
- 失败或用户取消不扣减，或自动退回；
- 同一文件加同一规则版本可命中缓存，减少重复成本；
- 记录 `UsageLedger`，后台可查、可调整；
- 对超长文档设置页数上限或额外扣费。

### 8.7 后台管理扩展

在现有管理后台增加：

- 审查规则 CRUD、导入导出、启停和版本发布；
- 规则集管理：按合同类型和立场组合规则；
- 提示词模板管理：版本、适用模型、变更记录；
- 模型路由：解析用便宜模型，审查用强模型，报告润色用中等模型；
- 审查任务监控：排队数、失败率、平均耗时；
- 用量统计：按用户、合同、模型、日期统计 Token 和成本；
- 质量抽样：人工查看模型结论，标记误报和漏报；
- 数据留存和删除策略配置。

### 8.8 安全与合规

- 所有合同文件按用户或团队隔离，接口层校验归属；
- 文件存储加密，下载使用短期签名 URL；
- 管理后台查看合同内容需要额外审计记录；
- 支持用户删除合同及关联解析结果和报告；
- 明确数据留存周期，默认不长期保存敏感合同；
- 提供隐私政策、服务条款和免责声明；
- 不将客户合同用于模型训练；
- 如需处理个人信息，遵守个人信息保护相关要求，并提供数据处理说明；
- 企业版可提供私有化部署或独立存储区域。

## 10. 90 天落地路线

以下路线按 1 至 2 名全栈开发者估算。如果只有一个人，建议把每个阶段延长 1 至 2 周，并砍掉 P1 功能。

### 阶段 0：产品定义与评测集（第 1 至 2 周）

交付物：

- 明确目标客户和首批合同类型，例如销售合同、采购合同、NDA；
- 收集 30 至 50 份脱敏合同样本；
- 定义 20 至 30 条高风险规则和风险等级；
- 人工标注 100 条条款级结论，形成黄金评测集；
- 完成数据模型和页面原型；
- 确定文件存储方案和模型预算。

验收：

- 团队对“审查什么、不审查什么”有一致口径；
- 每条规则都有明确触发条件和示例；
- 能用 10 份合同做人工基准。

### 阶段 1：文档链路（第 3 至 5 周）

交付物：

- 合同上传、对象存储、文件元数据；
- PDF / DOCX 解析和页码映射；
- 条款切分和条款列表；
- 异步任务框架和状态查询；
- 合同列表与工作台骨架。

验收：

- 30 页合同可稳定解析；
- 条款顺序和页码基本准确；
- 解析失败有明确错误和重试入口；
- 任务状态可追踪。

### 阶段 2：审查与报告（第 6 至 8 周）

交付物：

- 规则引擎和首批规则；
- 模型结构化审查；
- 风险清单、原文定位和处理状态；
- 合同内问答；
- Word / PDF 报告导出。

验收：

- 每份合同生成可读的风险报告；
- 高风险结论可定位到原文；
- 报告包含免责声明和规则版本；
- 审查结果可人工接受或忽略。

### 阶段 3：商业化与后台（第 9 至 10 周）

交付物：

- 文档额度、用量流水和扣减逻辑；
- 套餐权益与现有会员体系打通；
- 规则、提示词、任务、用量后台；
- 基础审计和删除能力；
- 试用用户和首批付费用户。

验收：

- 用户能完成上传、审查、导出、付费的完整闭环；
- 单份合同成本可统计；
- 超出额度时有清晰提示；
- 管理员能调整规则和查看失败任务。

### 阶段 4：评测与上线（第 11 至 12 周）

交付物：

- 黄金评测集回归；
- 误报、漏报和引用准确性分析；
- 提示词和规则迭代；
- 性能、成本和失败率优化；
- 隐私政策、服务条款、免责声明；
- 小范围上线和用户反馈。

验收：

- 核心风险召回率达到约定目标；
- 报告导出成功率稳定；
- 单份合同成本在可接受范围；
- 无跨用户数据泄露。

## 11. 评测指标与质量门槛

### 11.1 产品质量指标

建议维护一份 100 份左右合同、1000 条左右条款结论的黄金评测集。每次修改规则、提示词或模型后都跑回归。

| 指标 | 含义 | MVP 目标 |
| --- | --- | --- |
| 核心风险召回率 | 黄金集中高风险条款被识别出的比例 | 不低于 80% |
| 引用准确率 | 结论引用的条款和原文是否正确 | 不低于 95% |
| 误报率 | 被标记为风险但人工认为不成立的比例 | 不高于 20% |
| 结构化输出成功率 | 模型输出能被 Schema 正确解析的比例 | 不低于 98% |
| 报告生成成功率 | 审查完成后成功导出报告的比例 | 不低于 99% |
| 平均审查耗时 | 30 页合同的端到端时间 | 不超过 3 分钟 |

### 11.2 业务指标

| 指标 | 说明 |
| --- | --- |
| 上传到报告的完成率 | 衡量核心流程是否顺畅 |
| 首次报告导出率 | 衡量结果是否有价值 |
| 7 日复访率 | 衡量是否形成持续需求 |
| 付费转化率 | 从试用到付费的比例 |
| 单份合同成本 | 模型、存储和计算成本 |
| 单份合同毛利 | 收入减成本 |
| 风险接受率 | 用户接受建议的比例，反映结论可信度 |

### 11.3 评测方法

- 人工标注每份合同的高风险、中风险、低风险和缺失条款；
- 对模型输出做条款级匹配，而不是只看整体文字是否像；
- 统计不同合同类型、不同模型、不同规则版本的差异；
- 记录每次误报和漏报，沉淀为新的规则或提示词约束；
- 对高风险结论做人工复核抽样，避免只追求自动化率。

## 12. 定价与商业化建议

### 12.1 建议套餐

价格仅作为参考，正式定价应结合目标客户访谈和模型成本测算。

| 套餐 | 建议价格 | 权益 |
| --- | --- | --- |
| 免费试用 | 0 元 | 每月 3 份、每份 30 页以内、报告带水印 |
| 个人版 | 99 至 199 元 / 月 | 每月 20 至 30 份、完整报告、历史记录、合同问答 |
| 团队版 | 499 至 999 元 / 月 | 5 个席位、共享规则集、团队合同库、审计日志 |
| 企业版 | 按年报价 | 私有化或独立存储、API、专属规则、服务支持 |

### 12.2 收费要点

- 不要承诺无限量审查，否则模型成本不可控；
- 用文档份数加页数限制，比单纯按 Token 更容易被客户理解；
- 现有会员用户建议保留原权益或提供迁移方案，避免伤害老用户；
- 报告导出、版本对比、团队协作可以作为付费权益；
- 对高频用户提供按量包或年度折扣；
- 企业客户更看重数据隔离、审计和私有化，而不是更低价格。

### 12.3 首批获客

- 找 10 至 20 家中小企业做免费试用，换取脱敏样本和反馈；
- 与律所、财税、代理记账、创业园区合作，做初审工具；
- 用具体场景做内容，例如销售合同中最容易忽略的 5 个条款；
- 提供一次人工复核服务，快速验证产品结论是否可信；
- 不要一开始投放大规模广告，先把审查质量和报告体验打磨好。

## 13. 风险与应对

| 风险 | 表现 | 应对 |
| --- | --- | --- |
| 法律意见风险 | 用户把结果当成正式法律意见 | 明确辅助定位、免责声明、人工确认、高风险提示 |
| 模型幻觉 | 编造不存在的条款或依据 | 强制引用原文、结构化校验、低置信度标记、人工复核 |
| 解析质量 | 扫描件、表格、复杂版式导致漏读 | 解析质量评分、OCR、人工修正、限制支持格式 |
| 隐私与数据安全 | 合同包含商业机密和个人信息 | 加密存储、权限隔离、短期链接、删除机制、审计 |
| 成本失控 | 长合同、重复审查、恶意刷量 | 页数和任务限额、缓存、模型路由、并发限制 |
| 范围蔓延 | 同时做审批、电子签、CLM、团队协作 | 先做单点闭环，P1 和 P2 严格排期 |
| 模型依赖 | 供应商涨价、限流或接口变化 | 多模型配置、降级策略、超时重试、成本监控 |
| 评测不足 | 只靠感觉判断效果 | 建立黄金集、固定回归、记录误报漏报 |

### 13.1 高风险场景的处理

- 涉及重大金额、并购、跨境、诉讼或强监管行业的合同，提示用户必须由专业律师复核；
- 对模型无法确定的问题，输出需要人工复核，而不是给出肯定结论；
- 报告中区分规则命中、模型判断和人工确认三种来源；
- 保留审查时的模型、规则版本和提示词版本，便于追溯。

## 14. 现在不要做的功能

为了避免项目再次变成“功能很多但没有重点”，建议明确暂缓以下方向：

- 通用 Agent 平台、插件市场、工具编排；
- 图片生成、视频生成、语音克隆等多模态能力；
- 社交、动态、积分商城等与合同审查无关的功能；
- 完整电子签、审批流、合同全生命周期管理；
- 自研大模型或复杂微调；
- 一开始就做多行业、多语言、多司法辖区；
- 过早开发原生移动 App；
- 没有评测集就大规模接真实客户合同。

这些功能不是永远不做，而是在核心审查闭环和质量验证完成之前不做。

---

## 15. 备选方向

如果合同审查方向经过验证后不适合当前团队，可以考虑以下备选，但建议只选一个并做深。

### 15.1 制造业企业知识库

面向设备手册、维修 SOP、质量规范和售后工单，提供带引用的问答。优点是合规风险低于法律场景，缺点是通用知识库竞争激烈，必须绑定具体行业数据和工作流。

### 15.2 跨境电商客服

接入商品、订单、物流和退换货政策，生成多语言客服回复。优点是付费意愿明确，缺点是需要大量平台集成，且客服场景对实时性和准确率要求高。

### 15.3 教育题库与作业辅导

支持题目解析、错题本和个性化练习。优点是内容结构化程度高，缺点是内容合规、版权和教学效果验证成本不低。

### 15.4 暂不建议的领域

医疗诊断、投资建议、正式法律意见等高风险领域，不建议在缺少专业团队和合规体系时作为主方向。

## 16. 本周就可以开始的动作

### 16.1 产品侧

1. 选定首批合同类型，建议从销售合同、采购合同和 NDA 中选一个；

4. 确定审查立场：甲方、乙方或中立；
5. 写出 10 条必须命中的高风险规则。

```text
GET    /api/admin/review-rules            规则列表
```

接口设计要点：

- 上传和审查分离，审查是异步任务；
- 任务状态和结果分离，便于轮询和重试；
- 所有合同和报告接口都校验当前用户归属；
- 报告下载使用短期签名链接，不直接暴露存储路径；
- 管理端接口统一使用 `ADMIN` 角色守卫。

- 规则上线前必须有用例和回归测试。

## 总结

当前项目的价值不在于再增加一个通用聊天功能，而在于把已有的账号、会员、支付、模型、流式对话和后台能力，组合成一个垂直业务闭环。合同审查是最适合当前代码基础、付费意愿和交付形态的方向。

真正需要投入的不是更多页面，而是三件事：

1. **文档到条款的可定位链路**；
2. **规则加模型的可靠审查能力**；
3. **可导出、可审计、可计费的交付闭环**。

先把这三件事做扎实，再考虑团队协作、审批流和更多行业扩展。
